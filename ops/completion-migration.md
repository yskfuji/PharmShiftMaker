# 版2の追加移行・消去・復元

本変更の本番受入は未承認である。既存の版1入力・公開版と旧データを保持する。新たなモデルが存在することをもって自動移行はしない。

1. 接続先・原本を管理するシステム・復旧先を照合し、既存バックアップの内容ハッシュと一意な世代名を記録する。
2. 隔離先に同一のデータベース版を用意し、`alembic upgrade head` を実行する。追加版 `20260922_0004` は8表とジョブ計測3列を追加し、既存表の内容を削除しない。破壊的なダウングレード（downgrade）は拒否する。
3. 版1は版1のまま参照する。版2入力には各勤務の雇用改定・所定区間を明示する。契約順・他社勤務・休日暦・年休規則を推測により補完しない。ID件数・勤務秒数・付与日数・既存版のハッシュを照合する。
4. 登録は不変入力を作成する。契約や人事情報の更新後は「申請・実績を計画に反映」し、再検証・再確認する。旧確認では公開できない。
5. 給与金額、出勤率からの法定付与算出、人事原本の訂正は、原本を管理する外部システムの責任である。年休について外部の原本との差異がある場合、アプリ上の残数を通知なしにリセットしない。
6. 本番切替は未完了事項・施設根拠・IdP・代表データ・操作評価を確認した後に実施する。旧データベースへの逆変換を通常の切戻しとしない。新旧双方を保全し、新規イベントを喪失しない隔離再構築を選択する。

## 消去

現実装の消去対象は、**現行参照から外れた旧勤務入力と関連する下書き・公開版・ジョブ・監査通知・配送/閲覧記録の束**である。年休台帳が参照するものは止める。職員の全個人情報やダウンロード先のファイルを消去する機能とは異なる。

管理者が保存規則と期限を確認し、プレビューの対象数・参照・保全理由を確認する。実行時は同一のfingerprintを要求し、保全と参照を再照合する。消去前のハッシュ値・対象識別子を消去証跡として保持する。同一のハッシュ値のまま原本内容を書き換えない。消去対象の再現性を喪失することを結果に明示する。

## 旧バックアップからの復活防止

消去台帳の最新版は、復元するバックアップとは独立した保管場所に保持する。目録（manifest）に含むIDも管理対象であり、匿名加工情報とは呼ばない。署名鍵 `PHARMSHIFT_ERASURE_MANIFEST_KEY` は32 byte以上とし、コマンド引数として指定しない。

- 元環境において `python -m scripts.erasure_manifest export --file <未使用のmanifestパス>` を実行する。表示された目録のハッシュ値を独立した復旧記録に保存する。ファイルは0600で排他的に作成する。
- 既存の `backup_pipeline.py restore` は隔離データベースへ復元し、追加後のスキーマにおいては復元ゲートを隔離状態へ設定する。旧スキーマの復元は、アクセスの許可に先立ち、追加移行と `python -m scripts.erasure_manifest quarantine` を要する。
- **通常のAPI接続先への設定に先立ち** `python -m scripts.erasure_manifest apply --file <最新版manifest> --expected-hash <独立記録のhash> --result <新しい結果パス>` を実行する。旧バックアップに同梱されていたハッシュ値を最新版の根拠としない。
- 署名・期待ハッシュ値・対応する対象表を照合し、消去と利用停止状態を再適用する。失敗時はゲートを解除しない。権限者が結果を照合した上で通常アクセスへ進む。

本手順のモジュール試験は、本番バックアップ世代すべての在庫照合、鍵喪失や災害訓練、法的保全下における復元判断を完了した根拠ではない。
