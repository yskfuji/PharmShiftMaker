# 版2の追加移行、消去及び復元

本書は、入力の版2を扱うための追加移行、消去及び旧バックアップからの復元の手順を定める。

## 1. 前提

この変更の本番受入は、未承認である。既存の版1の入力及び公開版並びに旧データは、保持する。新しいモデルが存在することをもって、自動で移行することはしない。

## 2. 追加移行の手順

1. 接続先、正本及び復旧先を照合し、既存バックアップの内容ハッシュ及び一意な世代名を記録する。
2. 隔離先に同じ DB 版を用意し、`alembic upgrade head` を実行する。追加版 `20260922_0004` は、8表及び job の計測用の3列を追加し、既存表の内容を削除しない。破壊的な downgrade は拒否する。
3. 版1の入力は、版1のまま参照する。版2の入力には、各勤務の雇用改定及び所定区間を明示する。契約順、他社勤務、休日暦及び年休規則は、いずれも推測で埋めてはならない。ID の件数、勤務秒数、付与日数及び既存版のハッシュを照合する。
4. 登録では、不変の入力を作成する。契約又は人事情報を更新した後は、「申請・実績を計画に反映」を行い、再検証及び再確認を行う。更新前の確認のままでは公開できない。
5. 給与金額、出勤率からの法定付与の算出及び人事原本の訂正は、外部の正本の責任である。年休の正本に差異がある場合において、アプリ上の残数を黙ってリセットしない。
6. 本番切替は、残件、施設の根拠、IdP、代表データ及び操作評価を確認した後に行う。旧 DB への逆変換を、通常の切戻しとしない。新旧の双方を保全し、新規イベントを失わない隔離再構築を選ぶものとする。

## 3. 消去

現実装の消去対象は、**現行の参照から外れた旧勤務入力並びにこれに関連する下書き、公開版、job、監査通知及び配送・閲覧記録の束**である。年休台帳が参照するものについては、消去を止める。本機能は、職員の全ての個人情報又はダウンロード先のファイルを消去する機能とは異なる。

管理者は、保存規則及び期限を確認し、プレビューで対象数、参照及び保全理由を確認する。本ソフトウェアは、実行時に同じ fingerprint を要求し、保全及び参照を再照合する。

消去前のハッシュ及び対象の識別子は、消去の証跡として残す。同じハッシュのまま、原本の内容を書き換えない。消去対象の再現性を失うことは、結果に明示する。

## 4. 旧バックアップからの復活防止

消去台帳の最新版は、復元するバックアップとは独立した保管場所に保持する。マニフェストに含む ID も管理対象であり、匿名加工情報とは呼ばない。署名鍵 `PHARMSHIFT_ERASURE_MANIFEST_KEY` は32 byte 以上とし、コマンドの引数に書いてはならない。

復元は、次の手順で行う。

1. 元の環境で `python -m scripts.erasure_manifest export --file <未使用のmanifestパス>` を実行する。表示されたマニフェストのハッシュは、独立した復旧記録に保存する。当該コマンドは、ファイルを権限 0600 で排他的に作成する。
2. 既存の `backup_pipeline.py restore` は、隔離 DB へ復元し、追加後のスキーマでは、復元後の通常接続を遮断する状態（隔離状態）に設定する。古いスキーマの復元は、アクセスを許可する前に、追加移行及び `python -m scripts.erasure_manifest quarantine` を要する。
3. **通常の API 接続先に設定する前に**、`python -m scripts.erasure_manifest apply --file <最新版manifest> --expected-hash <独立記録のhash> --result <新しい結果パス>` を実行する。古いバックアップに一緒に入っていたハッシュを、最新版の証拠としてはならない。
4. 署名、期待ハッシュ及び対応する対象表を照合し、消去及び利用停止の状態を再適用する。失敗した場合は、通常接続の遮断を解除しない。権限者が結果を照合した後に、通常のアクセスへ進む。

> **注記**
> 本手順のモジュールテストは、本番バックアップの全世代の在庫照合、鍵喪失及び災害の訓練並びに法的保全下での復元判断を完了した証拠ではない。
