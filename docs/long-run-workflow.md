# 長時間実行（25か月正本）の進め方

作成日：2026-09-24。作業単位Aのr1〜r10の実績に基づき、非効率の原因と改善後の手順を整理する。

## 1. 実績（何に時間を使ったか）

- 25か月の本実行を10回実施し、合計150分を要した。最終の検証記録となったのはr9・r10の2回のみである。
  - 本実行の途中で初めて検出された不具合：r1・r2（ファイル一覧）、r7（現行入力の標識を消去）、r8（満了後日時が2038年）。
  - 実行方法の誤り：r5（満了後の再処理を同一の実行に混在させた）。
  - 環境の停止：r6（Dockerの仮想マシン）。
- バックエンドの全件試験（1回8〜15分）を4回反復した。
- 判断基準をv1〜v7まで改訂した。そのうち3回は、第三者的レビューが本実行の**後**に検出した問題が原因であった。
- 所要時間の内訳：25か月分のイベント処理は約40秒で完了する。時間の大半は、終盤の個人データの消去（1人あたり2〜8分）と、PITR・独立制御サービスの準備・照合に要している。

## 2. 原因

1. 反復の都度、本実行（PITR込み）を実施していた。終盤のみを短時間で試行する手段がなかった。
2. 第三者的レビューを本実行の後に実施していた。
3. 本実行に先立ち、Docker等の環境を確認していなかった。
4. 結果の確認を毎回手書きのスクリプトにより実施しており、見落とし（例：r7の消去表の内訳が空）が発生した。
5. 判断基準の改訂時に、他の計算（満了後日時等）への波及を確認していなかった。

## 3. 改善後の手順

1. **局所試験**：変更した部分の実PostgreSQL試験を実行する。
2. **高速ループ（開発用・合格の根拠ではない）**：`scripts/long_erasure_fastloop.py`
   - `capture`：消去イベント直前までの状態を一度のみ作成する（約40秒）。データベースは `pharmshift_audit_ckpt_*` である。
   - `replay`：その状態を複製し、終盤のイベントのみをレビュー担当付きで実行する。`--deferred-expiry` により満了後の再処理も実施する。
   - 結果には `scripts/subject_run_summary.py` の要約と不変条件が付される。違反がある場合は終了コード1となる。
   - マイグレーションが変更された場合は、`replay` が拒否する。`capture` を再実行する。
3. **第三者的レビューを本実行に先立って実施する**。
4. **事前点検**：`python -m scripts.long_run_preflight --output audit/<新しい実行ID>`。
5. **本実行は節目ごとに1回**：`scripts.long_pitr_workflows`（通常実行と `--deferred-expiry-only` は別実行）。全件試験は同一のコードにより並行して1回のみ実行する。
6. **結果確認**：`python -m scripts.subject_run_summary audit/<実行ID>`。不変条件の違反は、いずれも合格扱いとしない。
7. **判断基準を改訂する場合**：新たな規則が日時計算・集計・既存規則の選択に波及しないかを確認する。版を上げ、従前の版と結果は保持する。

## 4. 限界

- 高速ループは、物理PITR・独立制御サービス・復元・開放を含まない。制御サービスには上限付きの代替を使用する。したがって、受入の根拠にはならない。
- 不変条件は、現時点で判明している誤りの型のみを検出する。

## 5. 改善の実測（2026-09-24）

| 項目 | 改善前 | 改善後 |
|---|---|---|
| 消去直前までの状態の作成 | 本実行の都度約5〜30分（PITR込み） | `capture` 1回37秒 |
| 終盤イベントの再実行 | 本実行でのみ試行可能であった | `replay` 約4分（満了後の再処理なし）。結果は本実行r9と一致 |
| 消去イベント1回の処理時間（p0／p1） | 91秒／208秒 | 56秒／137秒 |

処理時間を短縮した変更（結果が同一であることを `replay` により確認した）：
- `database_erasure.dependency_plan` が、呼び出し元で計算済みのデータベースの一覧（inventory）を再利用する（従来は同一の一覧を2回計算していた）。
- `storage_routes.discover` が、内容に変更のないソースファイルの解析結果を再利用する。

計測により判明した、残りの処理時間の長い箇所は、`copy_graph.database_inventory` 内の `account_references`（約57万回呼び出される）と、`copy_coverage.coverage`（保存経路の照合）である。これらは処理容量（O06）の課題として残す。

試験の並列実行（pytest-xdist）は依存関係の追加を要するため、未導入である。
