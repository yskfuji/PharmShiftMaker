# 長時間実行（25か月正本）の進め方

作成日：2026-09-24。作業単位Aのr1〜r10の実績から、非効率の原因と改善後の手順をまとめる。

## 1. 実績（何に時間を使ったか）

- 25か月の本実行を10回行い、合計150分かかった。最終の検証記録になったのはr9・r10の2回だけである。
  - 本実行の途中で初めて見つかった不具合：r1・r2（ファイル一覧）、r7（現行入力の目印を消去）、r8（満了後日時が2038年）。
  - 実行方法の誤り：r5（満了後の再処理を同じ実行に混ぜた）。
  - 環境の停止：r6（Dockerの仮想マシン）。
- バックエンドの全件試験（1回8〜15分）を4回繰り返した。
- 判断基準をv1〜v7まで改訂した。そのうち3回は、第三者的レビューが本実行の**後**に見つけた問題が原因だった。
- 所要時間の内訳：25か月分のイベント処理は約40秒で済む。時間の大半は、終盤の個人データの消去（1人あたり2〜8分）と、PITR・独立制御サービスの準備・照合にかかっている。

## 2. 原因

1. 反復のたびに本実行（PITR込み）を回していた。終盤だけを速く試す手段がなかった。
2. 第三者的レビューを本実行の後に行っていた。
3. 本実行の前に、Dockerなどの環境を確認していなかった。
4. 結果の確認を毎回手書きのスクリプトで行っており、見落とし（例：r7の消去表の内訳が空）が起きた。
5. 判断基準の改訂時に、他の計算（満了後日時など）への波及を確認していなかった。

## 3. 改善後の手順

1. **局所試験**：変更した部分の実PostgreSQL試験を回す。
2. **高速ループ（開発用・合格の根拠ではない）**：`scripts/long_erasure_fastloop.py`
   - `capture`：消去イベント直前までの状態を一度だけ作る（約40秒）。データベースは `pharmshift_audit_ckpt_*` である。
   - `replay`：その状態を複製し、終盤のイベントだけをレビュー担当つきで実行する。`--deferred-expiry` で満了後の再処理も行う。
   - 結果には `scripts/subject_run_summary.py` の要約と不変条件が付く。違反があれば終了コード1となる。
   - マイグレーションが変わった場合は、`replay` が拒否する。`capture` をやり直す。
3. **第三者的レビューを本実行の前に行う**。
4. **事前点検**：`python -m scripts.long_run_preflight --output audit/<新しい実行ID>`。
5. **本実行は節目ごとに1回**：`scripts.long_pitr_workflows`（通常実行と `--deferred-expiry-only` は別実行）。全件試験は同じコードで並行して1回だけ回す。
6. **結果確認**：`python -m scripts.subject_run_summary audit/<実行ID>`。不変条件の違反は、どれも合格扱いにしない。
7. **判断基準を改訂するとき**：新しい規則が日時計算・集計・既存規則の選択に波及しないかを確認する。版を上げ、前の版と結果は残す。

## 4. 限界

- 高速ループは、物理PITR・独立制御サービス・復元・開放を含まない。制御サービスには上限付きの代替を使う。したがって、受入の根拠にはならない。
- 不変条件は、今分かっている誤りの型だけを検出する。

## 5. 改善の実測（2026-09-24）

| 項目 | 改善前 | 改善後 |
|---|---|---|
| 消去直前までの状態づくり | 本実行のたびに約5〜30分（PITR込み） | `capture` 1回37秒 |
| 終盤イベントの再実行 | 本実行でしか試せなかった | `replay` 約4分（満了後の再処理なし）。結果は本実行r9と一致 |
| 消去イベント1回の処理時間（p0／p1） | 91秒／208秒 | 56秒／137秒 |

処理時間を短くした変更（結果が同一であることを `replay` で確認した）：
- `database_erasure.dependency_plan` が、呼び出し元で計算済みのデータベースの一覧（inventory）を再利用する（従来は同じ一覧を2回計算していた）。
- `storage_routes.discover` が、内容が変わらないソースファイルの解析結果を再利用する。

計測で分かった残りの重い箇所は、`copy_graph.database_inventory` の中の `account_references`（約57万回呼ばれる）と、`copy_coverage.coverage`（保存経路の照合）である。これらは処理容量（O06）の課題として残す。

試験の並列実行（pytest-xdist）は依存関係の追加が必要なため、未導入である。
