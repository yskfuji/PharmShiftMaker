# 独立世代照合の導入と復旧の境界

本書は、独立した世代照合の導入手順及び復旧の境界について定める。

## 1. 適用範囲

本書の手順は、`control/witness.py` 及び `scripts/control_witness.py` の実装範囲を説明するものである。全保存経路、25か月の結合故障及び施設での本番受入は、完了していない。

既存の[独立制御手順](independent-control.md)も参照する。

## 2. 保存領域と権限

アプリ DB、消去制御 DB 及び世代照合 DB を分ける。世代照合 DB は `witness_checkpoint`、`witness_intents` 及び `witness_intent_resolutions` からなり、世代、操作ID、ダイジェスト及び状態を保持する。世代照合 DB は、人物の情報及び元の本文を受け取らない。

本ソフトウェアは、URL のホスト、ポート及び DB 名が同一の場合には、資格情報が異なっても拒否する。ただし、DNS の別名、同じ物理ボリューム及びバックアップ運用の独立性は、URL の検査だけでは証明できない。

アプリには、`PHARMSHIFT_CONTROL_*` 及び必要なマニフェストの署名鍵を設定する。アプリへ、制御の `operator` の資格情報並びに制御及び照合の署名用の秘密鍵を配布してはならない。

`PHARMSHIFT_WITNESS_URL/CLIENT/TOKEN/PUBLIC_KEY` は、制御サービスだけが使う。照合サービスには、独自の `PHARMSHIFT_WITNESS_DB_URL/PRIVATE_KEY/CLIENT/TOKEN` を設定する。

秘密鍵は32バイトの Ed25519 鍵の16進表記とし、トークンは32文字以上とする。本番の通信では、TLS を必須とする。開発用の資格情報及び証明書を本番へ流用してはならない。

## 3. 既存 DB を保全した初期導入

1. アプリ及び旧ワーカーの更新を止め、DB 及び管理ファイルのバックアップ並びに版、件数及びハッシュを保存する。新しい制御 DB、照合 DB 及び資格情報を用意する。
2. 制御 DB は、`python -m scripts.control_authority` で追加作成する。既存の `Head` をゼロへ戻してはならない。
3. 制御の全表が承認済みの移行内容であることを確認し、停止中の制御 DB から `authority_digest(session)` を算出する。運用の承認記録に、対象 DB、内容の照合及びダイジェストを結び付ける。巻戻しが疑われる DB の現在値を、無条件に初期の正本にしてはならない。
4. **未使用の照合 DB だけ**に対して、`python -m scripts.control_witness --verified-bootstrap-digest APPROVED_DIGEST` を実行する。既存のチェックポイントがある場合は、この処理は拒否される。この手順は、既存の台帳をリセットする手順ではない。
5. `uvicorn scripts.control_witness:build_app --factory` を起動し、次に照合への接続を設定した `uvicorn scripts.control_authority:build_app --factory` を起動する。いずれも、権限を制限した運用環境で起動する。production の制御サービスは、照合への接続がない場合には起動を拒否する。
6. `operator` の資格情報を持つ運用者が、`source` 及び `restore` のノードを登録し、アプリ、ワーカー及び CLI の資格情報と接続を切り替える。旧来の更新主体のうちテストの対象外であるものは、停止させてから開始する。切替えの完全な自動化、鍵の交代及び旧主体の失効の一巡は、未受入である。

マイグレーション0013は、型付きのアカウント参照をコピーの登録へ追加する。既存の行は変更しない。

既存のコピーへの人物の追加は、管理者が「既存記録の操作者参照を照合」でプレビューのハッシュを確認したうえで適用する。追加の際は旧来の対象者レビューを無効にし、原本のハッシュ及び保存の起算日は保持する。曖昧な対応を自動で確定しない。

## 4. 不確定処理と復旧

制御のトランザクションは、現在の制御 DB 全体のダイジェストを照合サービスと比較し、変更後のダイジェストを準備として記録してから制御 DB をコミットし、その後に照合側を確定する。

| 停止の位置 | 実装の挙動 | 運用上の境界 |
|---|---|---|
| 照合の準備前 | 制御 DB の変更をロールバックする | 同じ要求を再送できる |
| 照合の準備後、制御 DB のコミット前 | 未確定の状態を残し、アクセス及び復元の開放を遮断する | 時刻の経過では取り消さない。`operator` による `/witness/reconcile` は、同じ制御 Head のロック内で DB 全体のダイジェストを照合する。変更前イメージ（before-image）と一致すれば証跡付きの `ABORTED` を記録し、変更後イメージ（after-image）と一致すれば確定する。異なるイメージの場合は、遮断を維持する。この処理は、アプリの業務コミットが存在しないことの証明とは別である |
| 制御 DB のコミット後、照合の応答（ACK）前 | DB 全体が準備済みの変更後イメージと一致する場合に限り、照合側を確定する | アプリ側の消去コミットの証跡の照合は、別の制御プロトコルが担当する |
| 古い制御 DB に復元 | 独立した照合のダイジェストとの不一致により遮断する | 照合 DB まで同時に巻き戻された場合、及び全管理者権限が侵害された場合は、この構成だけでは防げない |
| 照合サービスとの通信断 | 個人情報の操作及び開放を停止する | 可用性への影響を含め、本番の冗長化及び訓練を要する |

`backup_pipeline.restore_command` は、ファイルの展開前に独立した隔離（quarantine）を要求し、DB の復元及びファイルの展開だけでは開放しない。

`restore_with_authority` は、最新のマニフェスト及び保全成果物を適用し、世代の比較を伴う開放（release）を要求する。世代が更新されていれば、開放は拒否される。

ネットワーク ACL 及び DB ロールによる隔離の自動導入、署名付き成果物の独立した配送サービス、並びに全保存先の走査の証明は、残件である。これらを、ソフトウェア上の関門だけで代替しない。

切戻しの際に、アプリ DB だけを戻して開放してはならない。照合 DB 及び制御 DB の新版を保全し、不確定の処理及び新しい消去を確認する。旧ファイル台帳を、別の更新の正本へ戻さない。

## 5. 検証した範囲

内部で実施した限定的なテストでは、独立した PostgreSQL と実際の HTTP、照合プロセスの SIGKILL、制御 DB の巻戻しの拒否、並びに2人の共有履歴及び1ファイルの復元・再適用を確認した。

個別の環境情報を含む生の実行記録は、公開候補に収録しない。この結果は、全共有型、25か月及び全障害行列の証明ではない。

## 6. 追加の移行と操作

通常の API 及びワーカーを停止して新版へ統一したうえで、独立した照合 DB にだけ追加の表を作成する。既存のチェックポイント及び意図の記録（intents）を、初期化し直してはならない。

```sh
.venv/bin/python -m scripts.control_witness --upgrade-resolution-schema
.venv/bin/python -m scripts.control_maintenance reconcile-witness
```

後者のコマンドは、`PHARMSHIFT_CONTROL_OPERATOR_ID/TOKEN` を持つ保守主体だけが実行する。

実際の3つの DB、HTTP 応答の喪失、並びに鍵及び主体の交代について限定的なテストを実施したが、個別の環境情報を含む生の実行記録は公開候補に収録しない。

二つのコマンドは、アプリ DB の業務トランザクションを強制停止しない。書込み元（`source`）を締め出した（fence）事実だけから、アプリ側が未コミットであると判定してはならない。
