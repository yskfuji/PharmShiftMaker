# 独立世代照合の導入と復旧の対象範囲

本手順は `control/witness.py` と `scripts/control_witness.py` の実装範囲を説明する。全保存経路・25か月結合故障・施設の本番受入試験は完了していない。既存の[独立制御手順](independent-control.md)も参照する。

## 保存領域と権限

アプリデータベース、消去制御データベース、世代照合データベースを分離する。世代照合データベースは `witness_checkpoint`、`witness_intents`、`witness_intent_resolutions`において、世代・操作ID・ハッシュ値（digest）・状態を保持する。世代照合データベースは人物や元本文を受け取らない。URLの同一ホスト・ポート・データベース名は、資格が異なる場合であっても拒否する。ただし、DNS別名、同一の物理ボリューム、バックアップ運用の独立性は、URL検査のみでは証明できない。

アプリには `PHARMSHIFT_CONTROL_*` と、必要な目録（manifest）の署名鍵を設定する。アプリへ、制御の運用担当者（operator）の資格や制御／照合の署名秘密鍵を配布しない。制御サービスのみが `PHARMSHIFT_WITNESS_URL/CLIENT/TOKEN/PUBLIC_KEY` を使用する。照合サービスには独自の `PHARMSHIFT_WITNESS_DB_URL/PRIVATE_KEY/CLIENT/TOKEN` を設定する。秘密鍵は32 byteのEd25519鍵のhex表記とし、トークンは32文字以上とする。本番通信はTLSを必須とする。開発用の資格や証明書を本番へ流用しない。

## 既存データベースを保全した初期導入

1. アプリ・旧ワーカーの更新を停止し、データベース／管理ファイルのバックアップと版・件数・ハッシュ値を保存する。新たな制御データベース・照合データベース・資格を用意する。
2. 制御データベースは `python -m scripts.control_authority` により追加作成する。既存Headをゼロへ戻さない。
3. 制御の全表が承認済みの移行内容であることを確認し、停止中の制御データベースから `authority_digest(session)` を算出する。運用承認記録に対象データベース・内容照合・ハッシュ値を結び付ける。巻戻しが疑われるデータベースの現在値を、無条件に初期の基準値としない。
4. **未使用の照合データベースのみ**に `python -m scripts.control_witness --verified-bootstrap-digest APPROVED_DIGEST` を実行する。既存checkpointが存在する場合、処理は拒否する。既存台帳のリセット手順ではない。
5. `uvicorn scripts.control_witness:build_app --factory`、次に照合接続を設定した `uvicorn scripts.control_authority:build_app --factory` を、権限制限した運用環境で起動する。productionの制御サービスは、照合接続がない場合、起動を拒否する。
6. 運用担当者がsource（書込み主体）／restore（復元先）を登録し、アプリ・ワーカー・CLIの資格と接続を切り替える。試験対象外の旧更新主体は、停止した上で開始する。切替の完全自動化・鍵交代・旧主体の失効一巡は、受入試験が未完了である。

マイグレーション0013は、型付きアカウント参照をコピー登録へ追加するものであり、既存行を変更しない。既存コピーの人物追加は、管理者の「既存記録の操作者参照を照合」においてプレビューのハッシュ値を確認した上で適用する。追加時は旧対象者レビューを無効にし、原本のハッシュ値と保存起算日は保持する。曖昧な対応を自動確定しない。

## 不確定処理と復旧

制御トランザクションは、現在の制御データベース全体のハッシュ値を照合サービスと比較する。次に、変更後のハッシュ値を準備記録した上でデータベースをコミットし、その後、照合側を確定する。

|停止位置|実装の挙動|運用上の境界|
|---|---|---|
|照合準備前|制御DB変更をロールバック|同一要求を再送可能|
|照合準備後・制御DBコミット前|未確定を保持し、アクセスと復元開放を遮断|時刻で取消しない。運用担当者の `/witness/reconcile` が、同一の制御headロック内においてDB全体のハッシュ値を照合する。before-imageと一致する場合は証跡付きABORTEDを記録し、after-imageと一致する場合は確定する。異なるimageの場合は遮断を維持する。これはアプリ業務コミットの不存在の証明とは別個である|
|制御DBコミット後・照合ACK前|DB全体が準備済みafter-imageと一致する場合に限り照合側を確定|アプリ側の消去コミット証跡の照合は別個の制御プロトコルが担当|
|古い制御DBに復元|独立照合のハッシュ値との不一致により遮断|照合DBまで同時巻戻しされた場合や全管理者権限侵害は、本構成のみでは防止できない|
|照合サービス通信断|個人情報操作と開放を停止|可用性への影響を含め本番の冗長化・訓練が必要|

`backup_pipeline.restore_command` は、ファイル展開に先立ち独立した隔離（quarantine）を要求し、データベース復元・ファイル展開のみでは開放しない。`restore_with_authority` は最新の目録・保全成果物を適用し、世代比較付きの開放（release）を要求する。世代が更新された場合、開放は拒否される。ネットワークACL・データベースロールによる隔離の自動導入、署名付き成果物の独立配送サービス、全保存先の走査証明は未完了事項である。これらをソフトウェアのゲートのみで代替しない。

切戻し時は、アプリデータベースのみを戻して開放してはならない。照合データベースと制御データベースの新版を保全し、不確定処理・新たな消去を確認する。旧ファイル台帳を、他の更新主体の拠り所へ戻さない。

## 検証した範囲

内部の限定試験においては、独立したPostgreSQLと実HTTP、照合プロセスSIGKILL、制御データベース巻戻しの拒否、2人共有履歴及び1ファイルの復元・再適用を確認した。個別の環境情報を含む生の実行記録は公開候補に収録しない。本結果は、全共有型・25か月・全障害行列の証明ではない。

## 今回の追加移行と操作

通常API・ワーカーを停止して新版へ統一した上で、独立照合データベースにのみ追加表を作成する。既存checkpoint/intentsを再初期化しない。

```sh
.venv/bin/python -m scripts.control_witness --upgrade-resolution-schema
.venv/bin/python -m scripts.control_maintenance reconcile-witness
```

後者は、`PHARMSHIFT_CONTROL_OPERATOR_ID/TOKEN` を有する保守主体のみが実行する。実3データベース・HTTP応答喪失、鍵・主体交代の限定試験を実施したが、個別の環境情報を含む生の実行記録は公開候補に収録しない。二つのコマンドは、アプリデータベースの業務トランザクションを強制停止しない。書込み主体（source）の書込みを遮断（fence）した事実のみから、アプリが未コミットであるとは判定しない。
