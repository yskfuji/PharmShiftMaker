# 隔離受入の実行・再開

本書は、隔離した環境における受入テストの実行及び再開の手順について定める。

## 1. 適用範囲

受入テストを、通常環境及び実データへ向けてはならない。必須の受入行及び依存関係の正本は、`ops/acceptance-cases.json` である。

診断行と受入行とを区別し、実行入口が未実装の行は `command: null` として残す。既存の局所テストを、全共有型、指定 BFS、25か月結合及び性能の代用にしてはならない。

## 2. 実行の手順

```sh
.venv/bin/python -m scripts.acceptance preflight
# 監査専用localhost PostgreSQL URLをPHARMSHIFT_TEST_PG_URLへ設定する。
# データベース名はpharmshift_auditで始まるものに限定する。
.venv/bin/python -m scripts.acceptance run \
  --directory audit/<新しい実行ID>/execution --case resume-public-api --detach
.venv/bin/python -m scripts.acceptance report --directory audit/<実行ID>/execution
.venv/bin/python -m scripts.acceptance resume --directory audit/<実行ID>/execution --detach
```

> **注記** 実行記録は `audit/` の下に書き出す。`audit/` は公開範囲外であり、本リポジトリの公開版には含まれない。

`--case` は、指定した行の依存行も実行する。終了コード0は、選択した行の成功を意味する。全受入の完了は、出力の `acceptance_complete` で別に判定する。

`preflight` は、前提の確認だけを行う。API 及び DB の疎通、資源の実測並びにテストの実行の成功の証拠にはならない。

## 3. 証拠と再開

実行のたびに新規のディレクトリだけを作成し、既存の証拠を上書きしない。

コード、フロントエンド、依存の定義、設定及び入力の生成器、並びに実行時の Python の主要な依存、DB の接続先及び探索スレッドを固定する。パスワードは、実行マニフェストへ記録しない。コード等が変わった場合は、新規の実行とする。

イメージの digest、実資源及び最終配布物の検査は、独立した必須の行である。ソースのハッシュの一致だけで、合格にしてはならない。

SQLite の実行台帳に開始及び結果を追記し、試行ごとのログ及び SHA256 を保持する。中断及び初回の失敗を、再試行で上書きしない。

成功したログが改変された場合は失敗となり、その依存行も合格ではなくなる。

親プロセスが SIGKILL されても、実行中の子プロセスが所有ロックを保持し、同じケースの二重実行を拒否する。子プロセスまで停止した場合は、開始だけが記録された試行を中断として残し、再試行する。

受入用の pytest の入口は、`scripts.acceptance_pytest` である。テストが0件であること、スキップ及び失敗は、いずれも合格としない。

汎用の実行器の終了コードだけでは、任意のコマンドの検証内容までは保証しない。各行の判定基準（`criterion`）、独立した期待値及びコマンドの対応をレビューする。

## 4. HTTP ジョブの再開

入力を再登録する前に、`GET /planning/jobs/by-key?scope_id=...&idempotency_key=...` を使う。同じ操作者、部署及びキーに限り、過去の入力のジョブも照会できる。

返却された入力のハッシュ、予算及び job ID を、保存済みのケースと照合する。該当するジョブが存在しない場合に限り、通常の登録及び受付へ進む。消去制御、認可及び入力の整合性の検査は維持する。

ケースの段階は、`GENERATED → REGISTERED → ACCEPTED → COMMITTED → OBSERVED` である。根拠のない飛越し、逆行、並びに別の本文、キー、予算又は job への置換を拒否する。

再起動の後に元の単調時計による受付の起点を失ったケースは、`elapsed=null` とする。機能の結果が正常でも、性能の成功にはならない。性能の最終判定には、初回の試行を用いる既存の `acceptance_assessment` も要する。
