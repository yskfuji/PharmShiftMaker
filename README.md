# PharmShiftMaker

病院薬剤部における勤務表作成、申請及び当日運用を支援する試作ソフトウェア

作成：2026年10月（リリースタグは付与していない。安定版の提供を表すものではない。）

## 要旨

病院薬剤部の勤務表作成、休暇・勤務交換の申請及び当日の配置変更を支援する試作ソフトウェアPharmShiftMakerを開発し、合成データを用いて動作を検証した。勤務表案は、契約、資格、必要配置その他の確認済み情報から、制約プログラミングにより生成する。生成した勤務表案は、ソルバーの制約式とは別に実装した検証処理で再検査する。編集、サーバー検証、確認及び公開は、版として記録する。2026年10月4日の継続的インテグレーションでは、バックエンドの自動試験1,327件及びフロントエンドの単体試験289件が合格した。一方、実施設での運用、ユーザビリティ評価及び支援技術を用いた実機による評価は実施していない。本ソフトウェアが示す勤務表案は人事・労務上の最終決定ではなく、有効性、安全性、使いやすさ及び法令適合は検証していない。

**キーワード**：勤務表作成、病院薬剤部、制約プログラミング、合成データ、オープンソースソフトウェア

## 1. 緒言

### 1.1 背景

勤務表作成は、必要人数の充足、休日の希望及び禁止される勤務の並びを同時に満たす組合せ問題である。これらの条件に限定した問題であっても、強い意味でNP困難であることが示されている<sup>1)</sup>。看護部門を対象とした国内の調査では、1部署1か月分の勤務表の作成に平均約11時間を要していた<sup>2)</sup>。ただし、この調査は1997年に看護部門で行われたものであり、現在の薬剤部門の状況を示すものではない。

勤務表作成の研究と実務との間には隔たりがある。看護部門の勤務表作成について、研究論文が扱ったシステムのうち実装に至ったものは30%にとどまると報告されている<sup>3)</sup>。

電子的な勤務表作成又は職員自身による勤務選択が職員又は組織に及ぼす影響については、系統的レビューが報告されている<sup>4,5)</sup>。一方のレビューが収載した18件は、記述的研究、非無作為化研究又は質的研究であり、著者らは無作為化比較試験及び縦断研究が必要であるとしている<sup>4)</sup>。同レビューは、影響はおおむね好ましいとしつつ、職員自身による勤務選択は固定の勤務表より公平性が低く、時間外労働の増加と関連したと報告している<sup>4)</sup>。他方のレビュー（23件）は、根拠は限られ、好ましい結果とともに、不利な結果又は変化なしとする研究もあると結論している<sup>5)</sup>。薬剤部門を対象として、勤務表作成ソフトウェアの効果を検証した国内の査読論文は、作成者が調べた範囲では見いだせなかった。

病院薬剤部門の夜間の勤務体制は、看護部門の交代制とは異なる。日本病院薬剤師会の令和4年度の調査（3,508施設）では、平日夜間の勤務体制がある施設は45.2%であり、体制の内訳は、宿直43.9%、オンコール38.7%、居残り体制24.3%、シフト勤務11.7%、二交代制8.9%、一部宿直4.0%及び三交代制0.9%であった（各体制の割合の合計は100%を超える）<sup>6)</sup>。したがって、看護部門の交代制を前提とした知見及びモデルを、そのまま薬剤部門に当てはめることはできない。

### 1.2 開発目的

本ソフトウェアの目的は、病院薬剤部の勤務計画、当日の変更、休暇・勤務交換、職員手続き及び監査記録を一貫して扱い、勤務表の作成者による確認作業を支援することである。効果の検証は本書の範囲に含めない。

### 1.3 位置付け

- 本ソフトウェアは試作段階にある。実施設での運用実績はない。
- 本ソフトウェアが示す勤務表案は、人事・労務上の最終決定ではない。給与計算、人事原本の決定及び適用法令等への最終的な照合は、導入機関又は外部システムの責務である。
- 本ソフトウェアは、疾病の診断、治療又は予防に使用されることを目的としていない。厚生労働省のガイドラインは、医療機関における一般事務作業の負担軽減等を目的とした院内業務支援プログラムを、医療機器に該当しない典型的な事例として挙げている<sup>7)</sup>。同ガイドラインは、勤務表作成を明示していない。また、本ソフトウェアの医療機器への該当性について、行政機関の判断は得ていない。
- 既定の構成は、患者情報を取り扱わない。

## 2. システム概要

### 2.1 構成

- FastAPI、PostgreSQL及びNext.jsによる業務機能と、合成データ用の試験環境を収録している。
- `src/shift_scheduler/config`及び`ops/attendance_mapping.example.yaml`の人物は、ID・表示名とも公開試験用の合成データである。導入時は、導入機関が管理する情報へ置き換える。
- 設定ファイルの部署名、勤務区分及び回数の上限は既定値である。導入機関の規程に合わせて定める必要がある。
- 新画面（開発名：認知中心UI v3）は、`IDEAL_UI=1` のときだけ `/workspace` で有効になる。既定値は無効（OFF）であり、既存画面を維持する。

### 2.2 勤務表案の生成方法

勤務表案の生成には、制約プログラミングのソルバーであるCP-SAT（Google OR-Tools）<sup>8)</sup>を用いる。

1. **決定変数**：候補となる勤務のそれぞれについて、割り当てるか否かを表す0-1変数を置く。
2. **ハード制約**：契約、資格、休暇、休憩、勤務間隔、労働時間、連続勤務及び必要配置に関する条件を、満たさなければならない条件として扱う。
3. **目的関数**：公開済みの勤務表からの変更数、希望に反する割当て（希望の順位で重み付けする）、負担の偏りの順に、辞書式に最小化する。上位の目的について最小であることを探索時間内に証明できない場合は、その時点の実行可能な案を返し、下位の目的は最小化しない。
4. **別実装による検証**：ソルバーが得た案を、ソルバーの制約式とは別に実装した検証処理で再検査する。違反が見つかった案は採用しない。ただし、契約の解決、資格の判定、休暇の算定その他の補助関数は、ソルバーと検証処理が共用する。
5. **探索時間**：1回の生成に指定できる探索時間の上限は300秒である（既定値は25秒）。

得られる解は、入力された候補、設定した制約及び目的関数の下での解である。目的関数は便宜上定めたものであり、得られた解が現場にとって最良であるとは限らない<sup>9)</sup>。

### 2.3 主要な画面

新画面は、次の8入口と25のブックマーク可能な子画面で構成する。

| 入口 | 主な用途 |
|---|---|
| 今日 | 対応が必要な判断、欠員、公開準備及び本人への通知 |
| 勤務表 | 月間勤務、日別表示、版差分及び本人用出力 |
| 計画 | 前提確認、候補生成、案比較、確認・編集及び公開 |
| 当日運用 | 予定、欠勤・交換、代替候補、承認及び通知 |
| 申請 | 本人の申請、休暇、勤務交換及び兼業・外部勤務 |
| 職員 | 職員一覧、本人アカウント、契約・資格及び入退職 |
| ガバナンス | 監査、実績照合、本人対応及び復旧状態 |
| 設定 | 外観、通知、欠勤時の同意及びフレックスタイム |

### 2.4 権限管理及び個人データの取扱い

- 役割は、薬剤師、責任者、管理者及び開発者の4種である。操作できる範囲は、役割並びに施設及び部署により制限する。
- 認証方式は、開発用の固定アカウントと、OpenID Connect（OIDC）の2種である。`PHARMSHIFT_ENV=production`を指定した場合は、OIDCを用いない起動を拒否する。
- 計画の生成、確認、公開その他の操作を監査記録として保存する。
- 個人データの消去機能と、復旧後に消去済みの個人データが復活しないことを確認する試験を収録している。
- 保存データの暗号化は、アプリケーション層では実装していない。暗号化の要否及び方法は、導入機関が定める。

## 3. 検証

### 3.1 方法

検証は、合成データだけを用いた自動試験により行った。対象は次のとおりである。

- バックエンドの単体試験、API試験及びPostgreSQLを用いた統合試験（pytest）
- フロントエンドの単体試験（Jest）及びブラウザー試験（Playwright）
- 静的解析（ruff、black、mypy、pyright、ESLint、TypeScript）
- GitHub Actions上の検査（CodeQL、秘密情報の検査、依存関係の脆弱性監査、プルリクエスト時の依存関係レビュー及び勤務表出力のCLIが確認・公開を迂回できないことの検査）

27業務シナリオ、認可、版競合、同一要求の再送（冪等性）、個人データの消去及び復旧の対象範囲の自動試験を収録している。

## 4. 考察

本ソフトウェアは、記録した合成条件の下で、自動試験の項目に合格することを確認した段階にある。以下の限界がある。

1. **試験結果の解釈**：試験結果は、記録された合成条件についての確認に限られる。自動試験の項目は無作為に抽出した標本ではないため、合格件数及びカバレッジを、故障率又は信頼性の推定値として解釈することはできない。
2. **未完了の評価**：30名のユーザビリティ評価、VoiceOver/NVDAを用いた実機による評価及び実運用相当の75パーセンタイル性能測定は未完了である。「使いやすい」「WCAG 2.2に適合」「本番運用が可能」又は「安全性を証明済み」とは扱わない。
3. **評価基準の統計的な限界**：計画しているユーザビリティ評価の合格基準を満たしても、不確かさが残る。例えば、30名で重大な誤確定が0件であっても、真の発生割合の95%信頼区間（Wilson法）の上限は11.4%である。詳細は[受入試験の基準一覧](docs/ideal-ui/acceptance-matrix.md)に記す。
4. **画面構造**：新workspaceの従来画面からの独立は未完了である。25子画面のうち6画面（申請の「休暇」「兼業・外部勤務」、職員の「契約・資格」、ガバナンスの「実績照合」「個人情報」、設定の「フレックス」）は、従来画面の実装を名称だけ変えて新しい外殻の中に表示している。また、25子画面のうち23画面を一つのClient Componentが振り分けており、画面構成の実装は用途別の`features/workspace`ではなく`ideal/screens`に残る。新画面で表示する部品の一部には、従来URLへのリンクも残る。検査の方法、結果及び完了条件は[検証記録](docs/ideal-ui/verification.md)の「Structural independence from the established screens」に記す。
5. **法令適合**：本ソフトウェアは、設定された規則に対する検査を行う。全ての勤務形態について法令適合を判定するものではない。雇用契約、就業規則、労使協定、宿日直の許可その他の適用条件との照合は、導入機関が行う必要がある。
6. **効果**：作成時間、公平性、満足度、時間外労働又は医療安全に対する効果は検証していない。1.1に示したとおり、既存の研究の根拠も限られる。
7. **適用範囲**：既存の研究の多くは看護部門を対象とする。宿直、日直及びオンコールが多い薬剤部門に、本ソフトウェアの制約の表現が十分であるかは、実施設で確認していない。

## 5. 結論

病院薬剤部の勤務表作成、申請及び当日運用を扱う試作ソフトウェアを開発し、合成データによる自動試験で動作を確認した。実施設での妥当性確認、ユーザビリティ評価及び支援技術による評価は今後の課題である。導入を検討する機関は、[利用上の注意](docs/legal/usage-notes.md)及び[導入・運用機関が確認すべき事項](docs/legal/operator-responsibilities.md)を確認すること。

## 付録

### 合成データでのローカル起動

継続的インテグレーション及び本手順は、Python 3.12、Node.js 24及びnpmを用いる。`pyproject.toml`が指定するPythonの版は3.11以上である。3.11での動作は、継続的インテグレーションでは確認していない。以下の手順は、隔離された開発用SQLiteと架空の職員（合成データ）だけを使用する。

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/python -m pip install --no-deps -e .
npm --prefix frontend ci
./scripts/generate-dev-certs.sh
```

ターミナル1で合成データ用のAPIを起動する。

```bash
.venv/bin/python -m scripts.remediation_test_server
```

ターミナル2で新画面を起動する。環境変数名のアンダースコアをエスケープせず、URLをMarkdownリンクにしないこと。

```bash
cd frontend
IDEAL_UI=1 \
NEXT_PUBLIC_API_BASE_URL=https://127.0.0.1:18510 \
NEXT_DIST_DIR=.next-local \
npm run dev -- --hostname 127.0.0.1 --port 18511
```

<https://127.0.0.1:18511/login> を開く。合成データ環境の開発用アカウントは次のとおりである。

| 役割 | ユーザーID | パスワード |
|---|---|---|
| 管理者 | `admin` | `pass-admin` |
| 責任者 | `leader` | `pass-lead` |
| 薬剤師 | `pharmacist` | `pass-ph` |

これらは、開発用の認証方式（`AUTH_MODE=mock`）における既定の資格情報である。このほか、開発者の役割の既定アカウント（`developer`）がある。上記の手順では、`scripts/remediation_test_server.py` が作る一時環境で用いる。`AUTH_MODE`を指定しない場合の既定は`mock`である。`PHARMSHIFT_ENV=production`を指定した場合に限り、OIDCを用いない起動を拒否し、開発用アカウントを無効にする。常設環境又は実データ環境で、開発用の認証方式及びこれらの資格情報を用いてはならない。証明書が信頼されない場合は、[開発用証明書の説明](certs/README.md)に従うこと。TLS検証を無効にする手順は採用しない。

### 検証コマンド

基本的な開発検査は次のとおりである。PostgreSQL統合、3ブラウザーによるE2E試験、視覚的検査、個人データの消去及び復旧演習には、別途、所有が確認された隔離用データベースと各実行手順が必要である。

```bash
ruff check src scripts tests devtools
black --check src scripts tests devtools
mypy src
pyright --project pyright-release.json --pythonpath "$(command -v python)"
python -m pytest

cd frontend
npm run lint
npm test -- --runInBand
npx tsc --noEmit
npm run build
npm run build-storybook
```

直近の検証記録は [docs/ideal-ui/verification.md](docs/ideal-ui/verification.md) にある。公開候補では、記録されたソースSHA-256と最終コミットが一致することを再確認する。過去の成功記録を変更後の合格として流用しない。
